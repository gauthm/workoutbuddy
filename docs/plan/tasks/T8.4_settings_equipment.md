## Objectif

1. **Section « Matériel » dans Paramètres = catalogue de matériel
   standard rangé par catégories**, avec cases à cocher :
   - chaque équipement peut être **décoché** individuellement ;
   - chaque **catégorie peut être décochée entièrement** (checkbox
     d'en-tête, état indéterminé si partiel) ;
   - **par défaut TOUT est coché** (l'utilisateur part du principe « j'ai
     tout », il décoche ce qu'il n'a pas chez lui) — voir règles de
     réconciliation plus bas.
2. **Détails éditables en ligne** avant enregistrement :
   - poids des **barres** (droite, EZ) et des **poignées d'haltères** ;
   - **poids unitaire et nombre de disques** — **une ligne par type de
     disque** (1,25 kg × 8, 2,5 kg × 6, 5 kg × 4...) ;
   - poids × nombre pour haltères fixes et kettlebells ; plage ± nombre
     pour haltères réglables et élastiques.
3. **Exposer la page existante** `#/equipment` (bouton « Vue complète ») —
   elle reste la référence pour les charges atteignables et les items
   libres.

**Contexte** : l'inventaire `equipment_item` alimente le prompt système
du coach et le moteur de progression (incrément minimal réaliste). Le
coach invite l'utilisateur à cocher son matériel réel (règles prompt :
T8.3). La page `#/equipment` existe depuis T1.7 mais est cachée.

## Principe de réconciliation (LE point critique)

Les lignes `equipment_item` créées depuis cette UI portent dans `notes`
un tag stable : `catalog:<instanceKey>` (ex. `catalog:plate_20`,
`catalog:dumbbell_fixed#2`).

Au montage :

```
load():
  items = GET /equipment
  tagged   = items dont notes commence par "catalog:"  → pilotent les checkboxes
  untagged = reste (créés par le coach ou EquipmentForm) → section séparée,
             listés en lecture seule avec bouton supprimer, JAMAIS touchés
             par l'enregistrement du catalogue

État des checkboxes :
  SI aucun item tagged N'EXISTE (première configuration de cette UI) :
    → TOUT le catalogue est coché par défaut, valeurs par défaut ci-dessous
    → l'utilisateur décoche ce qu'il n'a pas, ajuste les détails, Enregistrer
  SINON :
    → une ligne est cochée si un item tagged correspondant existe ;
      les lignes du catalogue absentes de la DB sont décochées,
      les champs pré-remplis depuis les valeurs DB.
```

Enregistrer (sync) — pour chaque **instance cochée du catalogue** :

```
pour chaque groupe, pour chaque item du groupe, pour chaque instance active :
  existante = tagged对应的 (par instanceKey)
  SI cochée ET !existante      → POST /equipment { category, name, ...champs,
                                   notes: 'catalog:' + instanceKey }
  SI cochée ET existante       → champs modifiés ? PUT /equipment/:id : rien
  SI !cochée ET existante      → DELETE /equipment/:id
puis toast + reload
```

Séquentiel (`for ... await`) — acceptable en local mono-utilisateur.
**Ne PAS toucher aux items untagged** (le coach a pu créer « Haltère
27kg récupéré chez Emmaüs » — il reste tel quel).

### Exigences comportement

- Checkbox d'en-tête de catégorie : coche/décoche tout le groupe ;
  état **indéterminé** (partiel) via `input.indeterminate` en directive
  maison ou `ref` + `watch` (Vue sans plugin — utiliser `:ref` callback :
  `(el) => el && (el.indeterminate = ...)`, motif acceptable).
- Ligne décochée → inputs `disabled` (grisés), valeur conservée en mémoire.
- `perPair` : label du poids = « poids par haltère » (clé
  `equipment.handle_weight_hint` existante).
- `count` disques : `min=2`, `step=2`, `title` = `equipment.count_pair_hint`.
- Bouton `+ paire` (repeatable) : ajoute une instance
  `dumbbell_fixed#2` avec mêmes defaults ; suppression d'instance
  (×) uniquement pour `#N`.
- Inputs contrôlés dans `state.rows[key] = { checked, weight_kg, count,
  weight_min_kg, weight_max_kg, weight_step_kg, resistance_min_kg,
  resistance_max_kg, id (si existant) }` — clé = instanceKey.
- Bouton « Enregistrer l'inventaire » `btn btn--primary btn--full` —
  exécute la sync (voir plus haut), disabled pendant l'envoi, toast
  `settings.equipment_saved` au final avec compte `{created, updated, deleted}`.
- Bouton « Vue complète » → `router.push('#/equipment')`.
- Section untagged : `EquipmentItemRow` ? NON — risque d'actions hors
  contexte ; liste texte simple + 🗑 avec `ConfirmModal` (réutilise
  `equipment.delete_confirm`).
- `EmptyState` inutile : le catalogue est toujours affiché.

### Sync (rappel des règles)

```javascript
async function save() {
  state.saving = true
  let created = 0, updated = 0, deleted = 0
  try {
    for (const row of Object.values(state.rows)) {
      const payload = buildPayload(row)   // { category, name, ...champs renseignés,
                                          //   notes: 'catalog:' + row.instanceKey }
      if (row.checked && !row.id)      { await api.create(payload); created++ }
      else if (row.checked && row.id)  { await api.update(row.id, payload); updated++ }
      else if (!row.checked && row.id) { await api.delete(row.id);    deleted++ }
    }
    store.showToast(t('settings.equipment_saved', { c: created, u: updated, d: deleted }), 'success')
    await load()
  } catch (err) {
    store.showToast(err.message, 'error')
    await load()   // resynchroniser l'état depuis la DB
  } finally { state.saving = false }
}
```

**Points d'attention :**
- `buildPayload` n'envoie QUE les champs pertinents de l'item (un banc
  n'a pas de `weight_kg` : ne pas envoyer `null` partout — l'API le fait
  déjà, mais rester propre). `name` : nom du catalogue (+ ` (2)` pour les
  instances `#N` répétées).
- `PUT /equipment/:id` : vérifier dans `equipment.js` si le PUT exige la
  totalité des champs ou accepte du partiel — adapter.
- NE PAS modifier `EquipmentView.js`, `EquipmentForm.js`,
  `EquipmentItemRow.js` ni l'API. Ils continvent d'exister pour la page
  complète et les actions du coach.
- Un item coach dont le nom ressemble au catalogue reste untagged —
  c'est voulu (pas de fusion automatique hasardeuse).
